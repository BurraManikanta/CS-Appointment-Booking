# Appointment Booking

A small Java 17 appointment-booking service with an in-memory store, a React UI built with Vite, and JUnit 5 tests.

## Requirements

- Java 17 or later

## Build and test

Run the automated test suite from the project root using the Gradle wrapper. The first run downloads the specified Gradle version.

```powershell
.\gradlew.bat test
```

On macOS or Linux, run:

```shell
./gradlew test
```

## Run the app

Start the Java API in one terminal:

```powershell
.\gradlew.bat run
```

In another terminal, start the React dev server:

```powershell
cd frontend
npm install
npm run dev
```

Open the URL Vite prints (usually [http://localhost:5173](http://localhost:5173)). Vite proxies `/api` requests to the Java API at `localhost:8080`. Set the `PORT` environment variable if you need to change the API port, and update the proxy in `frontend/vite.config.js` to match.

To create a production frontend bundle, run `npm run build` in `frontend`.

The UI calls these local endpoints:

- `POST /api/appointments` with JSON `{"providerId":"provider-1","start":"2026-11-01T10:00:00Z","durationSeconds":3600}` to book. Start must be a UTC timestamp ending in `Z`.
- `DELETE /api/appointments/{id}` to cancel. The JSON response includes `CANCELLED`, `NOT_FOUND`, or `ALREADY_CANCELLED`.

Booking returns HTTP 201; invalid input returns HTTP 400 and a time conflict returns HTTP 409. Data stays in memory and resets when the server restarts.

## Assumptions

- All appointment timestamps are `java.time.Instant`, representing absolute UTC instants. Local time zones and offset-free date-times are not accepted by the service interface.
- Appointment durations must be positive, and the calculated end time must be representable as an `Instant`.
- Appointments use half-open intervals `[start, end)`: adjacent appointments are allowed.
- Only active appointments for the same provider are checked for conflicts. Cancelling an appointment frees its slot immediately.
- Data is held in memory and is lost when the service process ends. The service is not backed by a database.
- A single in-process lock protects booking and cancellation operations against concurrent modifications.
- Booking IDs are generated by the service. Cancellation returns `CANCELLED`, `NOT_FOUND`, or `ALREADY_CANCELLED`; null or blank IDs are invalid input.
